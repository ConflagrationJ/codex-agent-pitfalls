# Codex / Agent 工作流避坑手册

> 版本 `v0.1.0`，记录于 2026-10-18。适用于 Codex Skill、子代理协作、浏览器扩展、自动化和 GitHub 发布。非官方文档，上游工具 schema 优先。

## 0. 先判断自己做的是哪一层

| 需求 | 正确形态 |
|---|---|
| 提示词、流程、模板、角色约束 | Skill |
| 真实工具、生命周期、后台服务 | 插件/扩展或服务 |
| 定时检查、提醒、轮询 | Automation / heartbeat |
| 独立执行、复核、并行读取 | 子代理 |
| 宿主没有的能力 | 不要伪装成 Skill；先接工具或降级 |

**P1｜把 Skill 当成运行时**

- 现象：`SKILL.md` 写了很多“自动执行”，实际仍然依赖模型主动读取和调用。
- 根因：Skill 是可加载的指令和资源，不是后台进程；自动调用也不等于强制执行。
- 做法：需要默认注入、后台任务或外部副作用时，使用宿主提供的插件、automation 或服务；Skill 只描述流程和决策边界。
- 验证：在一个没有显式提示技能名的新会话里，确认它是被路由加载，而不是只存在于文件夹。

## 1. Skill 安装与调用

**P2｜同名 Skill 导致无法解析**

- 现象：目录里能看到 Skill，但 `$skill-name` 或自动路由失效。
- 根因：多个目录的 `SKILL.md` frontmatter 使用同一个 `name`，解析器无法唯一选择。
- 做法：备份目录移出 `$CODEX_HOME/skills`，例如移到 `skills-backup`；Skill 根目录只保留一份。
- 验证：列出技能目录，确认 `name:` 唯一；开新会话再次解析。

**P3｜安装后当前会话看不到**

- 现象：文件已经安装，当前 chat 没有出现。
- 根因：技能元数据在会话启动时加载，之后新增的目录可能需要新 chat。
- 做法：安装后新开 chat；不要用当前会话的旧技能列表判断安装失败。
- 验证：新 chat 的 available skills 列表和实际调用都能看到。

**P4｜自动调用被误认为全局开关**

- 现象：`allow_implicit_invocation` 改了，但当前会话仍不自动使用。
- 根因：开关控制的是路由资格，不是模型必然执行；还受会话加载时间和 description 匹配影响。
- 做法：用 `agents/openai.yaml` 设置 `allow_implicit_invocation: true/false`；明确 `auto` 与 `explicit`；首次启用后用新 chat 验证。
- 验证：分别用匹配任务和无关任务测试，确认只有匹配任务被选中。

**P5｜把“自动调用”写成“始终执行”**

- 现象：用户认为所有任务都会被 Skill 接管，结果普通任务没有触发。
- 根因：自动调用是模型根据 description 的候选选择，不是无限优先级钩子。
- 做法：在 description 中写清适用和排除条件；需要强制执行的流程用宿主 hook/automation，而不是 Skill。
- 验证：记录一次匹配、一次不匹配的实际行为。

## 2. 子代理协作

**P6｜作者和复核者合并成一个人**

- 现象：代码写完后同一个代理说“我已复核通过”。
- 根因：作者会围绕自己的实现解释，复核失去独立性。
- 做法：撰写和复核必须是不同执行单元；高风险任务先过方案红队，再写代码。
- 验证：handoff 中保留 reviewer 身份、原始材料和结论。

**P7｜只写“建议”，没有可执行门禁**

- 现象：复核输出“建议关注并发问题”，任务仍然继续。
- 根因：没有严重度、触发条件、后果、反例和通过/打回。
- 做法：复核必须给严重度、证据、最小修复和 verdict；高危未清零不得执行。
- 验证：至少构造一个反例并证明它被拒绝。

**P8｜子代理之间直接聊天，破坏独立性**

- 现象：复核者先读到撰写者的结论，再“确认”实现。
- 根因：沟通路径改变了证据顺序。
- 做法：默认用文件 handoff；复核先看原始契约、diff、日志，再看作者摘要。
- 验证：handoff 有 task ID、base revision、原始输入和作者/复核者分离记录。

**P9｜没有版本和写范围**

- 现象：并行改动互相覆盖，旧证据被拿来批准新版本。
- 根因：缺少 task ID、base revision 和互斥 write scope。
- 做法：每个任务绑定 revision、写范围、验收和 evidence envelope；共享文件串行。
- 验证：reviewed revision 必须等于 executed revision。

**P10｜供应商/代理故障被当成任务失败**

- 现象：子代理返回 502 或上游连接失败，团队以为代码错了。
- 根因：模型/provider 代理故障属于基础设施层，不是实现结论。
- 做法：保留错误、重试或换执行单元；不要在故障结果上继续复核和发布。
- 验证：确认新执行单元能读取原 handoff，再从失点继续。

## 3. 浏览器与扩展

**P11｜刷新页面等于更新扩展**

- 现象：改了 `content.js`，刷新页面却仍运行旧逻辑。
- 根因：content script、background/service worker、manifest 和扩展权限是不同生命周期。
- 做法：content 改动刷新页面；manifest、权限、background、安装版本改动必须重载扩展；必要时重启浏览器。
- 验证：记录扩展版本、heartbeat 版本、权限和注入的脚本 hash。

**P12｜源码和运行 stage 不一致**

- 现象：测试加载源码通过，浏览器加载的却是旧 stage。
- 根因：扩展从 stage/缓存目录读取，源码只同步了一半，或者 launcher 复制时删掉了新文件。
- 做法：上线前校验 manifest 引用、source/stage 文件 hash 和启动器复制清单。
- 验证：测试直接加载实际扩展目录，不只加载根目录 helper。

**P13｜依赖 `window.open` 的弹窗**

- 现象：同样的链接有时能打开，有时没有 `NAV open`；重载/刷新后仍偶发。
- 根因：定时器里的 `window.open` 可能需要用户激活，且标签生命周期受弹窗策略影响。
- 做法：需要稳定批量导航时，用扩展后台的固定标签或宿主标签 API（例如 `tabs.create/update/remove`），并把任务 ID 绑定到标签。
- 验证：在没有手动点击的情况下，确认固定标签可以打开、落库、关闭，且不会误关用户标签。

**P14｜把 DOM 里“有卡片”当成任务成功**

- 现象：页面有 15 张卡片，但全部是重复或噪声。
- 根因：页面存在不等于出现新的、有效的目标。
- 做法：按唯一 job ID、相关性、完整正文和状态去重；记录“重复、噪声、风控、截断”各自的数量。
- 验证：成功条件必须由数据和事件链共同满足，不能只看页面元素数量。

**P15｜扩展权限和事件没有失败可见性**

- 现象：后台创建标签失败，runner 等到 45/60 秒超时才报错。
- 根因：`tabs.create/update/remove` 回调、用户手动关闭、加载错误没有统一广播。
- 做法：区分 auto-close、manual close、load error、replaced；每个 task 绑定 tab 和 link；失败立即通知 runner。
- 验证：模拟 create/update 回调丢失、手动关闭和 `chrome-error`。

## 4. 并发、锁与数据完整性

**P16｜用 unlink-then-create 竞争锁**

- 现象：两个进程都以为自己拿到了锁。
- 根因：删除旧锁和创建新锁不是原子动作，两个进程都能在空窗期获胜。
- 做法：让单进程服务端持有唯一 lease，或使用可证明原子的 OS lease；文件存在只作提示。
- 验证：两个真实子进程同毫秒 claim，只能一个成功。

**P17｜把中间状态文件当权威**

- 现象：旧 heartbeat/status 文件让人误判服务仍在运行或已经失败。
- 根因：状态文件没有过期时间、owner 或 generation。
- 做法：状态需要 TTL、token、generation 和明确 alive 检查；陈旧状态应归档，不应继续触发错误告警。
- 验证：进程退出、时间推进、旧 token 重放三种反例。

**P18｜用文本长度代替正文完整性**

- 现象：抓到 911 字公司介绍，被当成完整 JD。
- 根因：长度不等于招聘正文；缺少结构标记和尾部标记。
- 做法：正文完整性需要结构、来源、尾部、截断词和风控页联合判断。
- 验证：公司介绍、短正文、缺尾、登录墙、正常 JD 各有一条反例。

## 5. 验证与证据

**P19｜把静态测试说成真机验证**

- 现象：`node --check` 和 mock 全绿，就宣称功能已在浏览器工作。
- 根因：动态加载、权限、标签生命周期和页面时序不在静态测试覆盖内。
- 做法：明确区分 structural / behavior / real environment 三层；最后一层必须给实际日志或截图。
- 验证：报告里每一层都有独立的证据路径。

**P20｜缺少 revision 快照和行尾规范**

- 现象：同一目录在不同机器 hash 不同，复核失效。
- 根因：CRLF/LF、缓存、时间戳和未跟踪文件。
- 做法：使用 `git rev-parse` 或确定性 worktree snapshot；`.gitattributes` 固定 LF；忽略 `__pycache__`。
- 验证：同一内容跨平台 hash 一致，修改一个字节后 hash 变化。

## 6. 发布与 GitHub

**P21｜浏览器登录不等于 Git CLI 登录**

- 现象：网页已经登录 GitHub，命令行 `git push` 仍要求凭证。
- 根因：浏览器 cookie、Git Credential Manager、SSH key 是不同认证通道。
- 做法：先确认远端和认证方式；必要时由用户在凭据窗口完成一次授权；不要把 PAT 写进仓库。
- 验证：`git ls-remote` 能读到目标分支，推送后远端 commit 与本地一致。

**P22｜不同运行时共用一个发布仓库**

- 现象：核心 Skill 和宿主适配器的 tag、release、安装目录互相覆盖。
- 根因：两套运行时生命周期不同，却共用一个 release 名称和发布权限。
- 做法：核心仓库和宿主仓库分开；用 `core-v*` / `host-v*` 等命名空间；适配器固定核心版本。
- 验证：两边的 release 和安装路径能独立回滚。

**P23｜Release 只有标签，没有证据**

- 现象：有 tag，但用户不知道兼容哪个版本、验证了什么。
- 根因：没有 compat、commit、测试状态和安装说明。
- 做法：Release 写明版本、兼容 pin、commit、验证层级、已知限制和回滚方式。
- 验证：陌生人只看 Release 能判断能否安装。

## 7. 症状速查

| 症状 | 先查 |
|---|---|
| Skill 目录存在但 `$name` 不可用 | 是否有同名 Skill、是否新会话 |
| 自动调用不生效 | `agents/openai.yaml` 的 policy、description、会话加载时间 |
| 改代码后浏览器仍旧 | content 刷新 / 扩展重载 / background 重启是否混用 |
| 扩展测试过但真机失败 | 测试是否加载了实际 stage 和真实权限 |
| 偶发没有 NAV open | 弹窗用户激活、固定标签、tab 生命周期 |
| 两个采集器同时跑 | 是否只有一个服务端 lease，文件锁是否被误当权威 |
| 表格数字漂移 | revision、行尾、缓存、未跟踪文件和口径 |
| GitHub 网页登录但 push 失败 | Git credential / SSH / remote 是否独立 |

## 8. 最小验收清单

1. Skill frontmatter 名称唯一，安装后新 chat 可见。
2. 自动调用和显式调用各验证一次。
3. 子代理有 task ID、base revision、write scope 和独立复核。
4. 浏览器扩展 source/stage/manifest 引用一致，真实权限已生效。
5. 真实浏览器能看到 open、落库、关闭或失败事件。
6. 锁和并发只有一个权威来源。
7. Release 有兼容版本、证据和回滚说明。
